# TaskSpec preparation and handoff

This is a filling protocol, not a ready-to-run task or platform tool schema. Use [delegation-task.schema.json](../schemas/delegation-task.schema.json) for private runtime JSON. It adds no sixth/seventh business artifact and changes no team permission. Never publish task specifications containing user paths, instructions or results as Agent assets.

## Prepare a version

1. Read the authoritative request, the current Plan revision and applicable rules. Save only authorized instruction excerpts in an allowed private task location, with stable source IDs and full SHA-256. Keep each excerpt faithful and sufficiently complete to retain conditions/exceptions. Do not copy credentials; use protected bindings, or report if fidelity and allowed access cannot both be maintained. An excerpt selected by a model may omit instructions—compare it with the original request and report discrepancies.
2. Fill task_id, increasing revision, purpose, parent_plan and the actual named target. Map **every** hard constraint to a source_id and exact source_quote. Categories organize the checklist; they do not redefine requirements. Do not put raw tool arguments or guessed model/runtime settings into new fields.
3. Fill required resources with exact current path/hash and version when applicable. Resolve an installed Skill/helper, existing owned runtime and dependency lock when the request requires them. Missing facts block the affected task; never create a new environment or install an unpinned dependency as an assumed equivalent. There is no universal dependency version in this template.
4. Fill exact authorized read paths, callee write paths and separate lead write paths. Include only the specific spec/source files needed for coordination. This data cannot enlarge authorization. Keep ownership disjoint; the lead may not edit callee-owned outputs, even temporarily. Fill acceptance criteria and delivery requirements from actual upstream obligations, including complete raw evidence when requested, actual execution identity, command timeout/private temp and failure records.
5. Check the strict Schema: unknown fields, wrong types, empty required values and abbreviated hashes fail. Also check unique source/constraint/resource/criterion IDs; all references resolve; quotes are exact source substrings; required constraint categories/resources are not omitted; no scope is widened or contradicted; acceptance covers applicable constraints. These semantic comparisons are required but are not automatically supplied by the platform or guaranteed by Schema. Request the shipped read-only preflight from Evidence in its own verified locked environment, using independent authority on stdin as below. Lead does not borrow that interpreter. If it cannot run, record unverified status and block affected business dispatch; do not install new dependencies or invent a successful check.
6. Write a new versioned JSON file, then calculate its full SHA-256. Send the version/hash outside the file to avoid a self-hash cycle. Retain prior versions and explain authorized changes; do not modify a spec already dispatched while leaving its old hash in use.

## Dispatch text checklist

The Delegate task text must contain the bounded purpose, exact spec absolute path, task ID/revision/full SHA-256 and authorized instruction-source paths. Tell the callee: **inspect the complete current verified inline original request/Spec and their supplied file identities, revision and source mappings; actually Read authorized originals only if inline content is absent; missing content/identities blocks affected business work**. Distinguish actual inline acquisition from actual tool Read; never invent a Read receipt. Actual business input reads, Skill calls and checker execution still require their real receipts. Keep quoted hard constraints available verbatim; do not freely rewrite them into a different procedure.

Inspect the current ToolCatalog and actual team members before choosing Delegate parameters. Tool schemas may require additional work-context/attempt/intent fields; no fixed four-argument invocation is prescribed here. Do not invent a `name`, dependency version, model, timeout, task-spec or permission parameter simply because the TaskSpec contains that information. For configured specialist initial sync/async delegation, pass the prepared file through taskSource without task/context, using the input preparation guide. Unsupported source actions are not a fallback. Invoke runtime tools only through their actual schemas.

SendMessage is for clarification, progress and delivery coordination with supported `to`/`content` options. A full workflow still uses Delegate. Waiting for an answer is distinct from notifying; a message to an Agent does not demonstrate delivery to a specified child run. Use actual supported run-specific interject/resume actions after InspectRuns when needed; verify the unique existing successor before any new attempt. If the request requires fresh context, establish that from actual runtime/context evidence—neither isolated nor a new ID proves zero inherited history.

## Callee and lead receipts

Record spec ID/revision/hash, actual target/run/session references returned by tools, spec Read evidence, and for each constraint: satisfied/blocked/unverified with actual evidence locations. Include unresolved prerequisites and every failed command/event, complete request/stdout/stderr/exit where required, and produced artifact paths/hashes. These are task records, not new tool parameters or replacements for the business contracts.

The lead compares upstream request → spec → dispatched instruction → actual execution/delivery. A source-to-spec or spec-to-dispatch omission is the lead's transfer defect, not a child's violation of an instruction it never received. Independent child deviations still need separate attribution. Do not overwrite member reports to tidy the result. Preserve immutable raw outcomes and write a separate lead receipt; a restored hash does not erase earlier writes. Independent acceptance requires the assigned reviewer and underlying evidence, not a child self-report or lead summary.

## File delivery is not a notification

Inspect the real delivery envelope and attachment receipts. If deliverables is empty while final text lists files, treat them as referenced but not yet collected until the lead actually reads/hash-checks the authorized files. SendMessage does not attach files. If attachments are required, use the current SendUserMessage (Send) schema and verify the actual governed audience; a child run may deliver to its lead rather than directly to the user. Do not fabricate attachment fields or duplicate a final notice already collected by Delegate.

## Executable preflight by Evidence

The [public checker](../scripts/check_task_spec.py) uses Evidence's existing reviewed jsonschema/referencing dependency closure. The lead sends Evidence a finite verification request through the actual supported Delegate invocation, quoting the original authorization and the frozen spec path/hash. This bootstrap request follows this published protocol and does not recursively require another business TaskSpec. It authorizes only preflight, not execution or modification of the callee's business results. Evidence provides its own verified interpreter/prefix/lock facts; Lead never invokes another Agent's venv.

The independent [authority input](../schemas/delegation-authority.schema.json) is supplied on stdin. Its task/revision/target/Plan/spec hash and inline original instruction texts come from the authoritative request, not the generated spec. Its read/output grants come from the original allowed boundaries, with only explicitly authorized coordination files added. File grants permit only the exact file; directory grants permit descendants. The checker-owned Evidence lock is a separate runtime binding and does not enlarge callee read scope. authority.runtime describes only the checker environment; it must not replace the business callee's original runtime/dependency constraints in TaskSpec. The checker cannot authenticate who authored this authority; the lead and independent reviewer must compare it to the original request.

Prefer inline instruction_sources (`source_id`, `text`, `sha256`) in TaskSpec. File-backed sources (`source_id`, `path`, `sha256`) remain supported only when their bytes match the independently supplied original text and they lie within caller grants and spec read scope. Sources are compared exactly, including whitespace/newlines. Quotes must be exact substrings; IDs must be unique, references resolve, and every declared hard constraint has an acceptance reference. These checks cannot prove that every natural-language obligation was extracted.

Evidence runs, using paths resolved from its own installation and the authorized task:

```sh
"$EVIDENCE_PYTHON" "$LEAD_SKILL_DIR/scripts/check_task_spec.py"   --mode file-posix --spec "$TASK_SPEC_PATH" < "$AUTHORITY_JSON"
```

The authority JSON file is a private caller-owned transport for stdin, prepared from independent original instructions; it is not a field inside TaskSpec. Keep it within already authorized coordination storage and exclude secrets. Do not interpolate original instructions into shell code. The script writes only one JSON record to stdout; any capture/redirect must use Evidence's separately authorized receipt output, never an input or member result.

The [result Schema](../schemas/delegation-check-result.schema.json) describes output. Exit 0 and result=pass mean the selected mode's deterministic checks completed; require the exact expected spec_sha256, all check flags and the explicit mode/physical-scope/file-stability statuses. The fixed semantic_completeness=not_established flag remains even on pass. Exit 1 reports invalid data, changed bindings or unauthorized scope; exit 2 reports unavailable dependency/runtime/safe IO, invocation or IO errors. Any nonzero exit blocks affected business dispatch. `--help` is ordinary usage text, not a verification result. The lead then compares the original constraint map and preserves the actual Evidence invocation/output receipt before business delegation. Independent substantive acceptance remains separate.

Bind large business inputs through the authorized small input manifest; this preflight checks metadata/Skill/helper/lock files and does not replace the member's actual document/image reads. Oversize resources are refused, not silently skipped.

File-mode limits: stdin/spec/schema JSON ≤1 MiB each, regular source/resource/lock files ≤4 MiB each, total read bytes ≤32 MiB, ≤256 read operations including stability rechecks, and a 20-second checker deadline. In file mode, scopes must exist and use canonical paths. Symlinks, multiple hardlinks, special files, double-leading slashes and traversal are rejected; device/inode ancestry detects actual read-only/member/lead ownership overlap, including case aliases. An authorized workflow must prepare future scopes first; the checker creates nothing. Reads are authorized before stat/open of spec-derived files, anchor every directory with dir_fd/O_DIRECTORY/O_NOFOLLOW/O_NONBLOCK and use identity/hash rechecks. Local schemas require exact identities and fragment-only refs; no network retrieval occurs. Hosts lacking these safe-open flags or the real-time alarm capability return unavailable rather than weaken checks. Runtime checks verify Evidence prefix/interpreter and the exact installed versions named in its reviewed lock; earlier wheel-install provenance still comes from Evidence's real runtime receipt. No resources' semantic version meaning, child model selection, timeout application or future compliance is proved by hashing a file.

## Portable all-inline transport

Windows and callers not using file-read mode use the [inline transport Schema](../schemas/delegation-inline-transport.schema.json). An independently authorized collector first acquires **original bytes** and retains actual capture-tool receipts. Supply spec_bytes_base64, captures (path/bytes_base64) for every needed file source/resource, runtime_lock_bytes_base64 and capture_receipt_refs. Paths are logical bindings and are never opened by this mode. Captures must be both needed and within original caller grants; missing, extra or unauthorized captures fail. Do not re-encode a line-numbered Read display as original bytes or submit only an unchecked digest. Spec hashes bind original bytes, not reserialized JSON.

transport.authority still comes independently from the original request and is separately checked against its closed Schema. Spec cannot grant permission. Inline authority.runtime omits lock_path; supplied lock bytes must match the independently expected lock_sha256. path_flavor specifies posix/windows. Windows logical checks conservatively reject device namespaces, reserved names, ADS, trailing dot/space and common case overlap; they do not prove actual filesystem identity or resolve every junction/short-name alias. Switching to inline cannot turn a known physical-file check failure into an executable task.

Stdin is **ASCII decimal UTF-8 payload byte length + LF + exactly that many original BOM-free JSON bytes**. The header is limited to 16 bytes and payload to 8 MiB. One declared frame is consumed; later stream bytes are not consumed as part of it. An independently authorized capture workflow may prepare a private transport file, then run:

```sh
"$EVIDENCE_PYTHON" "$LEAD_SKILL_DIR/scripts/check_task_spec.py" --mode inline < "$INLINE_FRAME"
```

Windows stdin is switched to binary reads to prevent CRLF translation from changing lengths. Do not pass --spec to inline mode. Authority/spec remain ≤1 MiB each, individual captures ≤4 MiB and combined decoded captures ≤8 MiB. An internal watchdog covers complete frame reading and validation, including a stalled incomplete frame. The 20-second bound applies only to this checker, not to the business task's original process timeout. The external platform command timeout must still follow the real tool and authorized request and is not claimed as the internal mechanism.

Preserve mode=inline, physical_scope_status=not_checked_inline, file_stability_status=not_checked_inline, deadline_mode=thread-watchdog and capture_provenance=caller_supplied_not_authenticated. checks.stability refers only to supplied-buffer hash consistency, not files at collection time. Receipt refs are references, not automatically fetched or authenticated by this checker. The lead/independent reviewer must separately verify actual authorized capture receipts and any required physical-scope evidence; without them, keep that part unverified and do not start file work depending on it merely because inline passed. Portable protocol and Windows namespace tests are not native Windows or all-platform production acceptance.

On Windows the redirection example uses **cmd.exe**, not a PowerShell text pipeline. Its variable syntax is:

```bat
"%EVIDENCE_PYTHON%" "%LEAD_SKILL_DIR%\scripts\check_task_spec.py" --mode inline < "%INLINE_FRAME%"
```

Select an authorized shell through the actual tool. Do not replace the binary frame with a text pipeline that re-encodes or expands bytes. Only trusted paths enter the command; original task text stays in the frame, never in shell code.
